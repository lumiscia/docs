title: Beta notes
description: What can change while Lumiscia is in beta, and how to build an integration that copes.
---

Lumiscia is in beta. The API, SDKs, pricing, and limits can still change, and some changes may require code updates in your application. When a change breaks existing integrations, we try to document the migration path and keep the breakage small.

## What can change

- Pricing, plans, monthly credit, the per-render minimum, and rates.
- Concurrency, queue priority, and tier thresholds.
- Limits on duration, resolution, frame rate, node count, media size, media expiry, and artifact retention.
- SDK package names, exports, types, and helpers.
- API request and response shapes, error messages, webhook payloads, and event names.
- Renderer output for edge cases, and newly added nodes and output formats.

[Pricing](pricing) lists the current rates and tier limits, and [How it works](how-it-works#validation) lists the API limits. If you plan high-volume usage, treat beta pricing as guidance, not a contract, unless we have agreed on custom terms.

## Stability

Expect occasional problems while the platform changes:

- API downtime.
- Longer queue times during deploys or capacity changes.
- Failed renders from renderer regressions or unsupported media. The API checks an output format, alpha or bit depth against its rules before a worker encodes it, so an alpha video, a still or a 10-bit video it accepts can still fail, for example with `encode_failed`. A failed render costs nothing.
- Browser previews that differ from cloud renders in edge cases while the WebAssembly bindings evolve.
- Docs or dashboard changes that land before the matching SDK release.

## Render queues

A render can wait in `queued` before it moves to `processing`. Waits are longer when GPU workers are cold, when your workspace already has as many active renders as its tier allows, or during deploys. A [batch render](pricing#batch-renders) waits for idle capacity, and after 12 hours it is queued like a standard render. Queue time is never billed. See [Pricing](pricing#queue-priority) for concurrency per tier.

## Media and artifacts

Treat Lumiscia storage as temporary. Uploaded and URL-imported media expire after 24 hours, and you can [delete](guides/media-sources#delete-media) them sooner. Artifacts expire 1 day after the render on the free tier and 7 days after on paid tiers, and the artifact endpoint returns an error once they do. Keep your source assets and finished renders in your own storage.

URL imports can fail when the source is slow, unreachable, or too large.

## SDK versions

The SDK changes faster during beta than it will afterward. Pin an exact version, and read the changelog and [Upgrade to 0.6](upgrade-0-6) before you upgrade. Lumiscia renders Lumen 0.6 compositions, so use a 0.6 SDK:

```json title="package.json"
{
  "dependencies": {
    "@lumiscia/lumen-sdk": "0.6.0"
  }
}
```

Use the documented SDK methods for renders, media, progress, and artifacts. Don't depend on undocumented response fields.

## Building for beta

- Show render status in your UI instead of assuming a render starts right away.
- Show validation errors to the user. The error's `diagnostics` name the field or limit at fault.
- Store render ids and input hashes so you can trace a render later.
- Send an `Idempotency-Key` with each render request, so a retry never creates a second render. Without one, an identical request within 5 minutes still returns the existing render with `cached: true`. See [Billing in the API](pricing#billing-in-the-api).
- Use [webhooks](guides/webhooks) or `waitForRender` instead of tight polling loops.
- Run a short sample render before you submit many.

## Reporting issues

When you contact [support](help/support), include:

- the render id and workspace,
- the error `code` and `requestId`, if a request failed,
- the SDK version,
- the composition JSON, or a smaller one that reproduces the problem,
- the media type, codec, dimensions, and duration, if media is involved.
