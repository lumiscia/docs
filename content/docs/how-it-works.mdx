---
title: How it works
description: How Lumiscia validates a composition, evaluates its node graph, loads media, and renders frames.
---

Lumiscia renders compositions with Lumen, its open-source engine. A composition is a directed graph of nodes. Frames start at source nodes, pass through processing and compositing nodes, and end at a single `media_output` node.

## Compositions

A composition is a JSON object with four required fields:

| Field             | Contents                                                                 |
| ----------------- | ------------------------------------------------------------------------ |
| `timeline`        | `fps` (default 30) and `duration_frames`.                                |
| `render_settings` | Output `width` and `height` in pixels.                                   |
| `nodes`           | Graph nodes. Each has an integer `id`, a `type`, and optional `params`.  |
| `connections`     | Edges from a node (`from_node`) to an input port (`to_node`, `to_port`). |

The optional fields are `lumenSchemaVersion`, the Lumen version the composition was written for; `compositions`, named templates that `clip` nodes play; `functions`, reusable expression functions; `audio`, audio tracks and clips; and `metadata`, an object for your own data. See [Composition format](composition-format) for every field.

## Validation

The API checks each render request when you submit it, before it queues or charges anything. The composition must match the Lumen 0.6 [composition schema](composition-format), use only known node types and params, and stay within these limits:

| Limit            | Value                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------- |
| Frame rate       | Up to 60 fps                                                                                 |
| Duration         | Up to 10,800 frames rendered, which a [frame range](#output) can take from a longer timeline |
| Width            | Up to 3,840 px                                                                               |
| Height           | Up to 2,160 px                                                                               |
| Nodes            | 1 to 250                                                                                     |
| Composition JSON | 1 MB                                                                                         |
| Media            | Up to 50 manifest entries, and up to 50 distinct files counting `asset:<id>` references      |

The API accepts every Lumen 0.6 node type, including the [3D nodes](guides/3d). `lumenSchemaVersion` must be `0.6` or a 0.6 release such as `0.6.2`, and any other version is rejected with `document.schema_version`. A composition without the field is read as 0.6.

Your workspace tier can lower the resolution and duration limits. Free workspaces that have never topped up render up to 1080p and 2 minutes, counted over the frames a render covers. See [Pricing](pricing#queue-priority).

A composition that fails these checks gets a `400` response with the code `invalid_project_payload`, an `error` message, a `requestId`, and `diagnostics` that name what is wrong and where:

```json
{
  "code": "invalid_project_payload",
  "error": "composition node 3 has unknown parameter opactiy",
  "diagnostics": [
    {
      "code": "node.unknown_param",
      "message": "composition node 3 has unknown parameter opactiy",
      "node": 3,
      "path": "/nodes/2/params/opactiy",
      "severity": "error"
    }
  ]
}
```

`path` is a JSON pointer into the composition, and `node` is the node's `id` when there is one. Diagnostic codes such as `node.unknown_param` are stable; messages are not, so branch on the code. The SDK throws the response as a `LumenError` with the same `code`, `message` and `diagnostics`, so you can show them in a builder UI as is. Output settings that Lumiscia can't render get a `422` instead (see [Output](#output)). More media than the limit allows also answers `422`, with `media_manifest_too_large` and no `diagnostics`.

Lumen then checks the graph itself before it renders a frame:

- The graph has exactly one `media_output` node.
- Every node id is unique.
- Every connection points at an existing node and port, of the same kind.
- Every required input is connected, and an input that takes one source has at most one connection.
- The graph has no cycles.

A graph that fails these checks fails the render.

### Check before you render

`POST https://api.lumiscia.com/v1/renders/check` runs Lumen's checks, the media checks and the API's limits on a composition without creating a render, and isn't billed. Send the `composition` and, optionally, the `media` manifest and the output options (`output`, `codec`, `quality`, `bit_depth` and `alpha`) the render would use:

```bash
curl https://api.lumiscia.com/v1/renders/check \
  -H "authorization: Bearer $LUMISCIA_API_KEY" \
  -H "content-type: application/json" \
  -d @check.json
```

The response has `ok`, which is `true` when no diagnostic is an error, and `diagnostics`, the errors and warnings both. An output option the API can't take, such as `png_sequence`, `bit_depth: 12` or an unknown key in `output`, gets the same `422` as a render. A combination it rejects, such as `alpha: true` in an `mp4`, comes back as an error diagnostic, so `ok` is false. Its code is `invalid_output` or `invalid_quality`, or `settings.invalid` with the setting's `path` when the value is in `render_settings`. A warning such as `font.fallback`, for a font family the render won't have, doesn't make `ok` false. With a test API key, the check skips the media, as test renders do.

## Ports

Every port carries a `raster`, which is an image, or a `scene` of 3D objects, lights and cameras. Scene nodes output scenes, `render_3d` draws a scene into a raster, and every other node takes and outputs rasters. Shape, path, and text nodes output rasters directly, so you can connect them to any processing, compositing, or output node. A connection between different kinds fails with `connection.wrong_kind`.

## Frame evaluation

Lumen renders on demand. For each frame, it starts at `media_output` and walks upstream, evaluating only the nodes that frame needs:

- Nodes that don't connect to `media_output` never render.
- A `switch` node renders only its selected layer.
- A `time_remap` node requests only the source frame it maps to.
- A node whose params come out the same as on the frame before, and whose inputs are unchanged, reuses its earlier output, even when its params are expressions. Video `media_in` nodes, `wgsl_shader` nodes and a `model_3d` playing an animation render on every frame.

Most params accept an expression, which is a string that starts with `=`. Lumen evaluates expressions every frame with these globals:

| Global   | Value                    |
| -------- | ------------------------ |
| `frame`  | Current frame number.    |
| `time`   | Current time in seconds. |
| `fps`    | Composition frame rate.  |
| `width`  | Render width in pixels.  |
| `height` | Render height in pixels. |

```json
{
  "id": 4,
  "type": "transform",
  "params": {
    "translate_x": "=sin(time * 3.14159) * 120",
    "translate_y": "=frame * 0.5",
    "rotate": "=time * 12"
  }
}
```

See [Expressions](expressions) for operators, functions, and easing.

## Media

Nodes reference media by a manifest alias or by `asset:<id>`, never by a bare media id or a URL. A render request carries a top-level `media` manifest that maps each alias to an uploaded file:

```json
{
  "media": { "hero": "lumen:media_3f9a1c2b7d4e5f60" },
  "composition": {
    "timeline": { "fps": 30, "duration_frames": 150 },
    "render_settings": { "width": 1280, "height": 720 },
    "nodes": [
      { "id": 1, "type": "media_in", "params": { "kind": "video", "source": "hero" } },
      { "id": 2, "type": "media_output" }
    ],
    "connections": [{ "from_node": 1, "to_node": 2, "to_port": "source" }]
  }
}
```

`"source": "asset:media_3f9a1c2b7d4e5f60"` names the same upload directly and needs no manifest entry.

You get a media id by uploading a file to `POST https://api.lumiscia.com/v1/media` or importing a URL with `POST https://api.lumiscia.com/v1/media/url`. Lumiscia probes each file, and a render can use it only once its status is `validated`. Uploads expire after 24 hours. The API rejects a composition that puts an `http://` or `https://` URL in a media field, so import remote files first and reference them by alias. Uploads take images, video, audio and fonts; see [Media sources](guides/media-sources#what-you-can-upload) for the formats and what 3D and LUT sources can read.

A video `media_in` node can trim the source with `range_start` and `range_end`, change `speed`, and set a `loop_mode`. `range_end` is the first source frame past the range, and leaving it out plays to the source's end. Lumen works out which source frame each output frame needs before it renders, so workers and previews decode only those frames.

## Output

A render is an 8-bit MP4 of the whole timeline, with the composition's audio, unless you ask for something else. Set `output`, `codec`, `quality`, `bit_depth` and `alpha` in the render request, or `codec`, `quality`, `bit_depth` and `alpha` in [`render_settings`](composition-format#render-settings). The request's value wins. The Node SDK writes `bit_depth` as `bitDepth` and `jpeg_quality` as `jpegQuality`; the API takes the snake_case names.

| Setting               | Values                                   | Default                                                    |
| --------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| `output.format`       | `mp4`, `mov`, `webm`, `png` or `jpeg`    | `mp4`                                                      |
| `output.frames`       | `{ "start": 0, "end": 90 }`              | The whole timeline, or frame 0 for a still                 |
| `output.jpeg_quality` | 1 to 100, for `jpeg` only                | 90                                                         |
| `codec`               | `h264`, `hevc`, `av1`, `prores` or `vp9` | `h264` in an `mp4`, `prores` in a `mov`, `vp9` in a `webm` |
| `quality`             | `draft`, `standard`, `high`, `lossless`  | `standard`                                                 |
| `bit_depth`           | `8` or `10`                              | `8`, and ProRes is always 10                               |
| `alpha`               | `true` or `false`                        | `false`                                                    |

Each format holds these codecs and options:

| Format        | Artifact               | `codec`                         | `alpha` | 10-bit                                 |
| ------------- | ---------------------- | ------------------------------- | ------- | -------------------------------------- |
| `mp4`         | Video                  | `h264` (default), `hevc`, `av1` | No      | `hevc` and `av1`                       |
| `mov`         | ProRes 4444 video      | `prores`                        | Yes     | Always. `bit_depth: 8` is rejected.    |
| `webm`        | VP9 video              | `vp9`                           | Yes     | Without alpha. With alpha it is 8-bit. |
| `png`, `jpeg` | One frame, as an image | None                            | None    | None                                   |

A still takes no `codec`, `quality`, `bit_depth` or `alpha` in the request, not even `alpha: false`, and it ignores those keys in `render_settings`. The artifact downloads with the format's content type (`video/mp4`, `video/quicktime`, `video/webm`, `image/png` or `image/jpeg`) and a file name of `<render id>.<extension>`, where the extension is `mp4`, `mov`, `webm`, `png` or `jpg`.

Add the extra fields next to `composition` and `media` in the body of `POST https://api.lumiscia.com/v1/renders`. An alpha video, a still and a 10-bit video:

```json
{ "alpha": true, "output": { "format": "mov" } }
```

```json
{ "output": { "format": "png", "frames": { "start": 45 } } }
```

```json
{ "codec": "hevc", "bit_depth": 10 }
```

`frames` is `{ "start": 30, "end": 90 }`, which renders frames 30 to 89. `end` is not included. `start` defaults to 0 and `end` to the end of the timeline, or for a still to the frame after `start`. A still is one frame, so a range of more than one frame is an error. The 10,800-frame limit and a free workspace's 120-second limit count the frames a render covers, not the timeline's length, so a composition longer than either can still render a short range or a still.

An artifact can be at most 5,000,000,000 bytes. Before it queues a `mov`, the API estimates the file's size as `width` × `height` × frames × 0.6638 bytes, and rejects the render with `output_too_large` when the estimate is past that. A 1920×1080 `mov` can have at most 3,632 frames, and a 3840×2160 one at most 908. For example, 1,000 frames at 3840×2160 come to about 5.5 GB, so the API rejects them. Render fewer frames, a smaller size or a `webm`. The estimate can be higher than the real file, and a render of any format whose finished file is past 5,000,000,000 bytes fails with `output_too_large`. A failed render costs nothing.

The API rejects what it can't render with a `422` before it queues or charges anything, instead of rendering something else:

| Request                                                                                 | Code               |
| --------------------------------------------------------------------------------------- | ------------------ |
| `png_sequence`, `jpeg_sequence` or any other format name                                | `invalid_output`   |
| An unknown key in `output` or `output.frames`                                           | `invalid_output`   |
| `alpha: true` in an `mp4`                                                               | `invalid_output`   |
| A `codec` the format can't hold, such as `prores` in an `mp4` or `vp9` in a `mov`       | `invalid_output`   |
| `quality`, `codec`, `bit_depth` or `alpha` in the request with a `png` or `jpeg`        | `invalid_output`   |
| `jpeg_quality` with another format, or outside 1 to 100                                 | `invalid_output`   |
| An empty frame range, one past the timeline, or a still of more than one frame          | `invalid_output`   |
| A frame range that renders more than 10,800 frames or breaks your tier's length limit   | `invalid_output`   |
| A `codec` that isn't one of the five, or a `quality` that isn't one of the four presets | `invalid_quality`  |
| A `bit_depth` in the request other than 8 or 10                                         | `invalid_quality`  |
| 10-bit `h264`, 8-bit `prores`, or 10-bit `vp9` with `alpha`                             | `invalid_quality`  |
| `lossless` with `av1` or `prores`                                                       | `invalid_quality`  |
| A `mov` the size estimate puts past 5,000,000,000 bytes                                 | `output_too_large` |

When the value at fault came from `render_settings`, the response's `diagnostics` hold a `settings.invalid` diagnostic with the `path` of the setting, such as `/render_settings/alpha`. A render with no `output.frames` that breaks the 10,800-frame or length limit is a `400` with `invalid_project_payload` and a `limit_exceeded` diagnostic at `/timeline/duration_frames`, as in [Validation](#validation).

The API checks a request against these rules, not against the encoder. A render it accepts can still fail on the worker with a code such as `encode_failed`.

Billing doesn't depend on the format: a render costs the per-render fee plus its render time, and a failed render costs nothing. See [Pricing](pricing).

A render made with a test API key finishes with the same sample video whatever `output`, `alpha` or `bit_depth` you ask for, so a test key can't show you a still or an alpha video. The request is still validated as above.

Lumiscia has no route to cancel a render, so the SDK's `cancelRender` fails with a `404` and the code `route_not_found`. A render you no longer want still runs to its end.

## Rendering

The API queues each accepted render as `queued`. It stays `queued` until a GPU worker starts it, including while it waits for a free slot in your workspace's concurrency or, for a [batch render](pricing#batch-renders), for idle GPU time. The worker marks it `processing`, renders every frame it covers with `lumen-server`, encodes the output, and uploads it as the render's artifact. The render then ends as `succeeded` or `failed`.

A failed render has an `error` with a `code`, a `message`, and the `diagnostics` Lumen reported, when it reported any. A render that succeeded can carry `warnings` in the same shape, such as `font.fallback`.

You can wait for a render with `waitForRender(id, { onProgress })` in the SDK, which reads `GET https://api.lumiscia.com/v1/renders/{id}/progress` and uses the render's event socket only to hear about changes sooner. You can also use a [webhook](guides/webhooks), or poll `GET https://api.lumiscia.com/v1/renders/{id}`.

Download the artifact from `GET https://api.lumiscia.com/v1/renders/{id}/artifact` before `outputExpiresAt`. Artifacts last 1 day on the free tier and 7 days once your workspace has topped up or subscribed to Pro. Until the render succeeds, the endpoint answers `409` with `artifact_not_ready`, or with the render's failure code if it failed, and after expiry it answers `409` with `artifact_expired`.
