`@lumiscia/lumen-sdk` is the TypeScript client for the Lumiscia API. It sends your API key with every request, so use it only from trusted server code. It needs Node.js 22 or later, and the same import works in [Cloudflare Workers](cloudflare).

```bash
npm install @lumiscia/lumen-sdk
```

## Create a client

```ts
import { Lumen } from "@lumiscia/lumen-sdk";

const lumen = new Lumen({
  apiKey: process.env.LUMISCIA_API_KEY!,
  baseUrl: "https://api.lumiscia.com/v1",
});
```

| Option    | Type           | Description                                                                                          |
| --------- | -------------- | ---------------------------------------------------------------------------------------------------- |
| `apiKey`  | `string`       | Workspace API key. Sent as `Authorization: Bearer <key>` to the API's own origin.                    |
| `baseUrl` | `string`       | API root. The SDK appends paths such as `/renders` to it. Defaults to `https://api.lumiscia.com/v1`. |
| `fetch`   | `typeof fetch` | Custom `fetch` implementation. Defaults to `globalThis.fetch`.                                       |

## Upload media

Every media file a render uses must first exist in your workspace. Upload a local file with `uploadMedia`:

```ts
import { readFile } from "node:fs/promises";

const hero = await lumen.uploadMedia({
  body: await readFile("hero.png"),
  fileName: "hero.png",
});
```

`body` takes a `Blob` or `File`, a `Buffer` or other `BufferSource`, or a web `ReadableStream`. A `File` or a `Blob` with a type needs nothing else. A buffer also needs a `contentType`, or a `fileName` with a known extension such as `.png`, `.mp4` or `.wav`, and a stream also needs `sizeBytes`. If no content type can be found, `uploadMedia` throws `invalid_upload` before it sends a request.

Bodies over 64 MiB and every stream go up in 8 MiB parts, and anything smaller in one request. For a large file, `openAsBlob` from `node:fs` gives a `Blob` that is read as it uploads:

```ts
import { openAsBlob } from "node:fs";

const intro = await lumen.uploadMedia({
  body: await openAsBlob("intro.mp4"),
  fileName: "intro.mp4",
});
```

Or have Lumiscia fetch a public URL with `createUrlMedia`:

```ts
const plate = await lumen.createUrlMedia({
  fileName: "plate.jpg",
  url: "https://images.unsplash.com/photo-1546069901-ba9599a7e63c?w=1280&h=720&fit=crop",
});
```

Both return the media record. A render can only use media whose `status` is `"validated"`, and only until its `expiresAt` time. Uploads and URL ingest both run validation before they return, but if the validator is unavailable or a probe fails with a retriable error, `status` stays `"uploaded"`. Check `status` before you render.

See [Media sources](../guides/media-sources) for how renders reference media.

## Render a composition

Build the composition with `Composition` (see [Composition builder](../guides/composition-builder)), then pass it to `render` with a `media` manifest. Each manifest key is an alias that nodes reference, and each value is a media record from `uploadMedia` or `createUrlMedia`, or a `lumen:<media_id>` string, which `mediaReference` builds from a media record or id.

```ts title="render.ts"
import { Composition, Lumen } from "@lumiscia/lumen-sdk";

const lumen = new Lumen({
  apiKey: process.env.LUMISCIA_API_KEY!,
  baseUrl: "https://api.lumiscia.com/v1",
});

const plate = await lumen.createUrlMedia({
  fileName: "plate.jpg",
  url: "https://images.unsplash.com/photo-1546069901-ba9599a7e63c?w=1280&h=720&fit=crop",
});

const composition = new Composition({
  renderSettings: { width: 1280, height: 720 },
  timeline: { fps: 30, durationSeconds: 3 },
});

const image = composition.addNode({
  type: "media_in",
  params: { kind: "image", source: "plate" },
});
composition.addNode({ type: "media_output", inputs: { source: image } });

const render = await lumen.render(composition, { media: { plate } });

console.log("Render created:", render.id, render.cached ? "(cached)" : "");
```

`render` accepts a `Composition` or plain [composition JSON](../composition-format), and returns the queued [render](#read-a-render). Its options:

| Option           | Description                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| `media`          | Manifest of alias to a media record or `lumen:<media_id>`. Defaults to `{}`.                       |
| `webhookUrl`     | HTTPS URL that receives `render.succeeded` or `render.failed`. See [Webhooks](../guides/webhooks). |
| `signal`         | `AbortSignal` for the request.                                                                     |
| `idempotencyKey` | Sent as an `idempotency-key` header. The API currently ignores it.                                 |

If you send the same composition, media manifest, and `webhookUrl` within 5 minutes, the API returns the existing render with `cached: true` and doesn't start a new one.

## Wait for a render

`waitForRender` takes a render or its id and resolves with the finished render, or throws a `LumenError` if the render fails. Then download the artifact, an MP4 file, with `download`:

```ts
import { writeFile } from "node:fs/promises";

const done = await lumen.waitForRender(render, {
  onProgress: ({ status, progress }) => console.log(status, progress),
});

const artifact = await lumen.download(done);
await writeFile(`${done.id}.mp4`, Buffer.from(await artifact.arrayBuffer()));
```

`waitForRender` reads `GET /renders/:id/progress`, and between reads holds the render's WebSocket open for up to a minute to hear about progress sooner. When sockets fail, it reads the render every 5 to 30 seconds instead. Browsers can't send the socket's `Authorization` header, so there it only reads. `onProgress` receives `{ id, status, progress }`, with `progress` from 0 to 1, whenever the status or progress changes, and never goes backwards.

A rate limit never ends a wait. Every wait on the same `Lumen` client holds off for the API's `Retry-After`, or a growing delay without one. Server errors and network failures are retried with backoff, and end the wait only after ten minutes without a successful read. A 401 or 404 throws at once. Abort `signal` to stop waiting. To follow many renders at once, use [webhooks](../guides/webhooks) instead.

`download` returns the `Response` for the render's `url`, and sends your API key only when that URL is on the API's origin. Given an id, it reads the render first, and throws `render_not_ready` if the render has no artifact yet.

## Read a render

`render`, `getRender`, and `waitForRender` all return a `Render`:

| Field             | Description                                                              |
| ----------------- | ------------------------------------------------------------------------ |
| `id`              | The render id.                                                           |
| `status`          | `queued`, `processing`, `succeeded`, or `failed`.                        |
| `progress`        | From 0 to 1. Set by `waitForRender`, not by `getRender`.                 |
| `url`             | Absolute URL of the artifact, once the render has succeeded.             |
| `error`           | `{ code, message, retryable? }`, when `status` is `failed`.              |
| `cached`          | Set by `render`: whether an earlier identical request answered this one. |
| `costMicros`      | Render cost in millionths of a US dollar.                                |
| `outputExpiresAt` | When the artifact expires. `download` fails after that time.             |
| `createdAt`       | When the render was created.                                             |
| `inputHash`       | Hash of the render's input. Include it when you report a problem.        |
| `organizationId`  | The workspace that owns the render.                                      |

## Methods

| Method                                               | Returns      | API route                                                      |
| ---------------------------------------------------- | ------------ | -------------------------------------------------------------- |
| `render(composition, options?)`                      | `Render`     | `POST /renders`                                                |
| `getRender(id, { signal }?)`                         | `Render`     | `GET /renders/:id`                                             |
| `waitForRender(renderOrId, { onProgress, signal }?)` | `Render`     | `GET /renders/:id/progress` and `GET /renders/:id/socket`      |
| `download(renderOrId, { signal }?)`                  | `Response`   | The render's `url`                                             |
| `uploadMedia(options)`                               | Media record | `POST /media`, then `PUT` to `uploadUrl` or a multipart upload |
| `createUrlMedia({ url, fileName?, signal? })`        | Media record | `POST /media/url`                                              |

`uploadMedia` takes `body`, `fileName`, `contentType`, `sizeBytes`, and `signal`. The package also exports `mediaReference`, [`verifyWebhook`](../guides/webhooks#verify-signatures), and everything in `@lumiscia/lumen-shared`, including `Composition` and the expression helpers.

The API also has `GET /v1/media/:id`, which the SDK doesn't wrap yet.

## Errors

Every method throws a `LumenError` when a request fails or a render it waits on fails. An aborted `signal` rejects with the abort reason instead.

```ts
import { LumenError } from "@lumiscia/lumen-sdk";

try {
  await lumen.render(composition);
} catch (error) {
  if (error instanceof LumenError) {
    console.error(error.code, error.message, error.requestId);
  }
  throw error;
}
```

| Field          | Description                                                                      |
| -------------- | -------------------------------------------------------------------------------- |
| `code`         | The API's error code, or one the SDK sets (below).                               |
| `message`      | The API's error message. A validation error names the field or node that failed. |
| `status`       | The HTTP status, when the failure was a response.                                |
| `requestId`    | The API's request id, when it sent one. Include it when you contact support.     |
| `renderId`     | The render the error is about, such as the one `waitForRender` was waiting on.   |
| `retryable`    | Whether the server expects the same request to succeed if you retry it.          |
| `retryAfterMs` | How long the API asked you to wait, from its `Retry-After` header.               |

When the failure never reached the API's error handling, `code` is `http_<status>` (for example `http_502`), `network_error`, `invalid_response`, `render_not_ready`, or `socket_error`. `uploadMedia` throws `invalid_upload` for a body it can't send.
